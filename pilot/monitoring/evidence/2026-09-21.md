# Pilot monitoring implementation and live verification, 2026-09-21

Monitoring is installed on `laptop-dell-studio` as six separate systemd user
services: Prometheus, Loki, Alloy, the metadata exporter/local alert receiver,
Grafana, and Alertmanager. No existing controller was reconfigured or restarted.
All monitoring HTTP listeners and Loki gRPC bind to `127.0.0.1`. Alertmanager gossip
is disabled. The secondary pause marker remains present.

## Passed acceptance

- The final log proof, `pilot-observe-bb2b21476f`, was found in Loki after its Pod
  was deleted. Its `excluded-payload` line was absent. An earlier successful proof
  was `pilot-observe-304511ec92`. No proof Pods remain.
- Alloy collected 32 real lifecycle journal entries. Stored messages contain only
  a fixed `controller-event` prefix and a known state/error category. Raw provider
  messages and addresses were not retained.
- Prometheus recorded pending work (observed peak 11), running Pods, admission
  histograms, worker state and controller health during the load runs.
- Run `kv-1e523c0c9bbbfcda` passed smoke, 4/8/16-Job bursts, four sustained Jobs for
  ten minutes, and cleanup. Its complete measurement lasted 978.9 seconds over
  66 samples. Minimum laptop available memory was 2,019,680,256 bytes (1.88 GiB).
  Swap-in remained 0 pages; swap-out remained 238 pages throughout. All four
  existing systemd controllers stayed active. The existing validation suite and
  its timeouts were not modified.
- Grafana provisioned the 15-panel dashboard and both healthy data sources.
  All 18 panel queries succeeded through Grafana's authenticated data-source proxy.
- `PilotDeliveryTest_4cbfaf0c` fired from a real Prometheus rule and reached the
  local receiver. After its expression changed to false, the same alert delivered
  a resolved notification. The temporary rule was then removed.
- Final inspection found all six monitoring services and four original controller
  services active, with zero automatic restarts. Monitoring cgroups used about
  628 MiB combined at that snapshot. Swap counters were still unchanged; no active
  alerts or temporary proof rules remained.
- Live RBAC checks denied Secrets, Pod exec, kube-system Pod logs and node proxy
  access to the reader. Pilot Pod logs and the single application metrics proxy
  were allowed. No administrator credential is embedded in a running monitoring
  service.

## Retained development failures and limits

The first load run, `kv-23d0b2fe51162ece`, hit the unchanged two-minute admission
limit for one Job in the 16-Job burst. Its sustained phase and every cleanup passed;
controllers remained active and swap did not increase. The recorded workload had
quota but its autoscaler capacity check was Pending. Autoscaler logs reported
capacity not found and node-group limits reached. Replaying the recorded suspended
states through the admission harness reproduced the timeout. The root cause is
not established; the unchanged retry passed, which does not prove the underlying
admission intermittency is fixed. Full raw evidence remains under the laptop's
`~/kubernetes-validation/runs/` directories. The summary of the first failure is
preserved alongside the successful measurement here.

The first log proof exposed Alloy's retained newline in Kubernetes log entries.
The allowlist was corrected to permit trailing whitespace while still excluding
payload text, then the proof passed. Grafana's initial 256 MiB budget timed out
under MemoryHigh throttling; the 384 MiB trial also reached its soft threshold.
The final 512 MiB limit with MemoryHigh at 90% started successfully and passed
health, provisioning and query checks. No OOM kill was observed in these trials.

The initial alert proof removed its firing rule and waited for automatic expiry,
which exceeded its test timeout. The corrected proof exercises the real false-rule
transition before removal. Both test alerts had cleared at final inspection.

The resource measurement under the full bounded load was performed before Grafana
and Alertmanager were started. Post-addition verification covers startup, all panel
queries, local alert delivery, service health and unchanged swap counters; it is
not another ten-minute load run or a long-term soak. This is an isolated evaluation,
not a production performance or availability claim. Email delivery is not configured.

## Argo CD deliberately blocked

The gate sampled management capacity five times over one minute after dashboard
and alert checks. Available management memory was 1,864,372,224 to 1,868,079,104
bytes (about 1.74 GiB), below the required 2 GiB: 1536 MiB of active Argo CD container
limits plus a 512 MiB reserve. CPU and requested-resource checks passed, but the
memory check did not. No Argo namespace, CRDs or workloads were installed. No
controllers were moved onto disposable workers.

The pinned namespace-scoped Argo CD manifests, restrictive project/RBAC, manual
sync configuration, private-repository credential input, test application and
GitHub Actions image workflow are implemented and offline-validated. The local
HTTP image build passed response, health, metrics and log checks with a read-only
filesystem and all capabilities dropped. The repository is private; a scoped
read-only Git credential and an actual reviewed GHCR image digest are still
required once management capacity is adequate. GitHub publishing, Argo deployment,
health reporting and Git-revert rollback have **not** been proven and are not
reported as passed. No fake image digest was committed.
