# Isolated pilot validation, 2026-09-21

The suite ran manually on `laptop-dell-studio`, outside Kubernetes, against
`laptop-wifi-PROTOTYPE` (`kube-system` UID
`507117e6-f7ed-4307-a016-4ecc9a28b519`). Primary was available; secondary remained
paused. No host was resumed, powered off, or reconfigured by the suite.

## Confirmed live behavior

- Smoke: queued admission, DNS resolution, worker placement and completion.
- Queueing: quota reservation, excess demand waiting, cancellation removing owned
  Jobs/Pods/Workloads, and reservation release after completion.
- Impossible demand: both over-quota and unsupported-selector requests stayed
  suspended without capacity expansion.
- Placement: fitting work reused the existing primary worker.
- Services: DNS, Service and Pod-IP connectivity, readiness-gated endpoints, and
  allowed/denied NetworkPolicy traffic. The positive connectivity control passed
  again after the denied test.
- Load: bursts of **4, 8 and 16 Jobs**, then **four Jobs running for the complete
  ten-minute duration**, all passed with cleanup. Requests and limits remained
  250m CPU, 128 MiB memory and 64 MiB scratch per Job.

The full successful load run was `kv-0f17e2db75e3ee48`: 33 Jobs completed, including
its mandatory smoke Job. Total run duration was 980.8 seconds. Server timestamps
showed workload creation-to-admission p50 **7 s**, p95 **108 s**, maximum **109 s**;
Pod creation-to-Ready p50 **2 s**, p95 **3 s**, maximum **4 s**. Job duration includes
the intentional 30-second burst or 600-second sustained execution. Existing-node
creation-to-Ready timestamps include earlier node history and are not worker
provisioning latency. No performance gate is inferred from this single baseline.

## Prerequisites and unverified scope

Two-host packing, overflow, consolidation and lifecycle tests need an unpaused
secondary. Zero-worker scaling needs zero initial workers and zero unpaused
provider targets. Fresh-PVC storage needs an explicitly configured disposable
Delete StorageClass. Those prerequisites were not manufactured for validation.
The existing retained storage proof was not reused. Worker-recreation persistence,
physical shutdown, production migration and other future capabilities remain in
[the coverage matrix](../coverage.json) and [issue #113](https://github.com/TusharSariyaOrg/aws-account-infra/issues/113).

## Development failures retained in evidence

- `kv-00694858463a68a7`: the first 16-Job burst exceeded the admission clock;
  concurrent status updates also caused cleanup resource-version conflicts.
  Cleanup retry passed after the implementation was corrected to refresh only
  the same UID and run ownership. The original failure remains in its report.
- `kv-c1a3f860280b2643`: a probe was OOM-killed because dirty scratch page cache
  plus tmpfs allocation crowded the 128-MiB cgroup. The run was interrupted and
  final cleanup passed. The probe now budgets both allocations together, leaving
  at least one quarter of memory for overhead, without increasing resource limits.
- The corrected 4/8/16 burst and ten-minute run passed. The earlier admission
  timeout did not recur, and its two-minute limit was not relaxed.

These were harness development runs, not deliberate node-exhaustion or failure
injection. Complete JSON, Markdown, JUnit and raw event evidence is retained under
`~/kubernetes-validation/runs/<run-id>/` on the laptop. Copies of reports are in
this checkout's ignored `validation/kubernetes/runs/` directory.
