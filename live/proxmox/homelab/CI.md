# Proxmox deployment through GitHub Actions

The existing `tofu-plan` and `tofu-apply` workflows now support `proxmox-homelab`.
OpenTofu runs on a GitHub-hosted Ubuntu runner; the VMs run on pve. State remains
in the existing AWS backend at `proxmox/homelab/terraform.tfstate`.

## Plan and apply behavior

- A relevant same-repository PR triggers an authenticated Proxmox plan. AWS units
  retain their existing plan jobs. Both must pass the existing `plan-gate`.
- The Proxmox plan job declares `environment: prod` to match the Tailscale OIDC
  subject. It uses the AWS plan role for S3 state/locking and the limited plan
  `homelab-tofu-plan@pve!provider` token for Proxmox. A permission preflight rejects
  VM or disk write privileges on the planned resources.
- A maintainer reviews the posted plan, then adds the existing `apply` label.
  The serial apply job joins Tailscale only if Proxmox is among the changed units,
  uses the separate scoped write token, and dispatches the correct variables for
  each cloud. AWS receives `aws_profile=`; Proxmox receives
  `vm_creation_approved=true`. It then follows the existing auto-merge behavior.
- Apply computes a fresh plan at execution time, as the existing AWS workflow
  does. It does not consume a binary artifact from the PR plan job. Recheck plans
  if code or live state changes. No saved Proxmox plan is published as an artifact.
- `prod` currently has no required-reviewer protection. The apply label is the
  current deployment trigger, not a separate environment approval. Same-repository
  workflow authors with environment-secret access remain trusted; separate tokens
  limit normal plan operations, not malicious workflow changes by such authors.
- Fork PRs cannot run the privileged Proxmox plan/apply. A selected Proxmox plan
  that is skipped or fails does not pass `plan-gate`.

This PR enables the deployment mechanism; it does not itself approve creating
VMs. Without an apply label, the preview does not allocate disks or start guests.
The proposed VMs are still stopped by default. Boot and Talos bootstrap are later
reviewed configuration changes.

## Reproduce GitHub configuration

In the Tailscale admin console, create `tag:github-ci` owned by the administrator.
Create an OpenID Connect trust credential with:

| Field | Value |
| --- | --- |
| Issuer | `https://token.actions.githubusercontent.com` |
| Subject | `repo:TusharSariyaOrg/aws-account-infra:environment:prod` |
| Scope | Auth Keys write (`auth_keys`) |
| Tags | `tag:github-ci` |
| Audience | Generated by Tailscale |

The operator supplies the resulting client ID and audience. Store them as GitHub
repository variables `TS_OIDC_CLIENT_ID` and `TS_OIDC_AUDIENCE`. They are public
identifiers, not authentication secrets. Existing variables `TOFU_PLAN_ROLE_ARN`
and `TOFU_APPLY_ROLE_ARN` provide AWS OIDC role selection. No additional AWS access
keys, IAM resources, or permanent Tailscale auth key are needed.

The action is pinned to the reviewed v4 commit
`306e68a486fd2350f2bfc3b19fcd143891a4a2d8` with Tailscale 1.102.4. It enrolls
an ephemeral tagged runner and performs cleanup after the job. Both workflows
request `id-token: write`. The Tailscale credential is restricted to the exact
repository/environment subject, not arbitrary GitHub repositories.

The operator-accepted allow-all tailnet network policy still applies to the CI
runner. The tag is an identity, not a network restriction. This setup does not
activate the previously deferred restrictive policy or retag the Proxmox host.
The runner reaches the existing private HTTPS Serve endpoint; no port is exposed
publicly and no router port-forwarding is needed. Proxmox and the direct LAN router must be on.

Provision the limited plan API identity from a trusted administration checkout:

```bash
python3 scripts/proxmox-provider-bootstrap.py --plan --ssh-target root@10.0.0.92
```

This creates `homelab-tofu-plan@pve` with privilege separation, system audit,
VM/guest-agent audit limited to IDs 100/102, and storage audit. It saves the token
as `~/.config/aws-account-infra/proxmox/plan-credentials.json` (0600). The existing
write identity remains in `credentials.json`. From an authenticated GitHub CLI:

```bash
python3 scripts/proxmox-ci-secrets.py
```

This sends the two token values directly over stdin to GitHub environment `prod`
as `PROXMOX_PLAN_API_TOKEN` and `PROXMOX_APPLY_API_TOKEN`, without printing them.
The helper validates both local file permissions and identity prefixes first.
Neither credential is committed or placed in command arguments.

## Recovery and verification

Recreate the Tailscale tag/trust through independent administrator access, then
update the two repository variables. If pve is rebuilt or a token is lost,
follow ACCESS.md to regain trusted root access and reissue API credentials.
To revoke only the reader, run `pveum user token remove homelab-tofu-plan@pve provider`
on pve, then recreate it using `--plan` and update GitHub secrets. Keep tokens
outside Git; do not depend on recovering their old values to restore CI.

Verify a same-repository PR can enroll an ephemeral runner, pass authenticated
HTTPS/scope checks, initialize the AWS backend, and produce a Proxmox plan. Actual
apply behavior and VM boot are separate acceptance checks. The clean-machine
restore rehearsal remains deferred and untested.

Sources: [Tailscale GitHub Action](https://tailscale.com/docs/integrations/github/github-action),
[workload federation](https://tailscale.com/docs/features/workload-identity-federation).

## Existing-volume inspection permission

PVE 9.2.11 requires `VM.Config.Disk` for GET requests inspecting VM disk
volumes. The pinned provider makes those calls during refresh. Therefore the
plan identity is **not strictly read-only**: it has disk-configuration access
only on VMs 100 and 102, in addition to audit permissions. It has no
VM.Allocate, VM.PowerMgmt, Sys.Modify or Datastore.AllocateSpace. Trusted
repository workflow authors remain a security boundary. Do not use
`-refresh=false` to hide drift or substitute the full apply token.

Fresh setup uses `proxmox-provider-bootstrap.py --plan` (the old `--read-only`
flag remains an alias). To upgrade the original identity once, run as root on
pve after inspecting existing roles and ACLs:

```bash
pveum role add HomelabTofuPlanVM --privs 'VM.Audit VM.GuestAgent.Audit VM.Config.Disk'
pveum acl modify /vms/100 --users homelab-tofu-plan@pve --roles HomelabTofuPlanVM --propagate 1
pveum acl modify /vms/102 --users homelab-tofu-plan@pve --roles HomelabTofuPlanVM --propagate 1
pveum acl modify /vms/100 --tokens 'homelab-tofu-plan@pve!provider' --roles HomelabTofuPlanVM --propagate 1
pveum acl modify /vms/102 --tokens 'homelab-tofu-plan@pve!provider' --roles HomelabTofuPlanVM --propagate 1
pveum acl delete /vms/100 --users homelab-tofu-plan@pve --roles HomelabTofuReadVM
pveum acl delete /vms/102 --users homelab-tofu-plan@pve --roles HomelabTofuReadVM
pveum acl delete /vms/100 --tokens 'homelab-tofu-plan@pve!provider' --roles HomelabTofuReadVM
pveum acl delete /vms/102 --tokens 'homelab-tofu-plan@pve!provider' --roles HomelabTofuReadVM
```

To revoke this capability, restore the old audit-only ACLs before removing the
new role's ACLs. Live refresh of existing disks will then fail. No token
rotation is required for either ACL change.
