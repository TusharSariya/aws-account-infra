# Backup authentication and certificate lifecycle

When `create_backup_identity = true`, this deployment adds a dedicated backup CA trust anchor, one IAM upload role,
its policy attachment and a Roles Anywhere profile. The role requires the exact
anchor ARN, account ID and certificate subject CN. The upload policy is also its
permissions boundary: attaching an extra policy cannot grant restore/delete
permissions. Sessions last at most one hour. The existing ECR identity is unchanged.

This is a proposed procedure, not evidence of enrollment or a successful backup.
Apply through the reviewed GitHub Actions plan and `apply` label workflow. No actual CA or
client key is generated by OpenTofu. The public CA input must be supplied when identity creation is enabled
on every plan/apply; omitting it then fails validation. The checked-in tfvars
disable identity creation for manual backups. Do not turn creation off after
enrollment unless intentionally deleting the identity; use
`backup_identity_enabled = false` to suspend new sessions.

## 1. Create the dedicated CA on the signing computer

Use OpenSSL 3 (`openssl version`; on a Homebrew Mac it is available at
`/opt/homebrew/opt/openssl@3/bin/openssl`). Run from the reviewed repository root.
Set `BACKUP_CA_DIR` to an **absolute path outside the checkout** on the signing
computer. These creation commands deliberately refuse existing directories.

```sh
umask 077
BACKUP_CA_DIR="$HOME/.config/aws-account-infra/backup-ca"
mkdir -p "$(dirname "$BACKUP_CA_DIR")"
mkdir -m 700 "$BACKUP_CA_DIR" || exit 1
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 \
  -aes-256-cbc -out "$BACKUP_CA_DIR/ca.key"
openssl req -new -x509 -sha256 -days 3650 \
  -key "$BACKUP_CA_DIR/ca.key" -out "$BACKUP_CA_DIR/ca.crt" \
  -subj '/CN=homelab-backup-ca' \
  -config config/environments/aws/staging/homelab-recovery/openssl.cnf \
  -extensions ca_extensions
openssl x509 -in "$BACKUP_CA_DIR/ca.crt" -noout -subject -dates -fingerprint -sha256
```

OpenSSL prompts for the CA passphrase. Keep it in an independently recoverable
password manager, never in shell arguments, tfvars or Git. Preserve the encrypted
CA key, public certificate and reviewed config in independent encrypted storage.
Losing this CA does not prevent restoring S3 data with the independent AWS login;
a new CA and uploader can be enrolled. A direct CA-to-leaf chain needs no
intermediate certificate or `--intermediates` argument. `pathlen:0` prevents this
CA from signing subordinate CAs.

## 2. Generate a leaf key and CSR on the backup execution host

Initially use a normal administration/backup host outside Talos. Do not try to
install a shell or credential helper into Talos, and do not deploy the CA key to
the uploader. A later Kubernetes backup service needs its own workload delivery
and runtime integration. Set the CN to the value in the reviewed tfvars.

```sh
umask 077
BACKUP_CLIENT_DIR="$HOME/.config/aws-account-infra/backup-uploader-01"
mkdir -p "$(dirname "$BACKUP_CLIENT_DIR")"
mkdir -m 700 "$BACKUP_CLIENT_DIR" || exit 1
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 \
  -out "$BACKUP_CLIENT_DIR/client.key"
openssl req -new -sha256 -key "$BACKUP_CLIENT_DIR/client.key" \
  -subj '/CN=homelab-backup-uploader-01' \
  -out "$BACKUP_CLIENT_DIR/client.csr"
```

The leaf key is unencrypted for unattended use; directory 0700/file 0600 and the
backup process account protect it. Transfer only the CSR to the signing computer
via authenticated SSH or an equivalent authenticated channel. Verify its origin
and exact subject against the intended host before signing. No shared leaf key.

## 3. Sign and return only the public certificate

Set `BACKUP_CSR` and `BACKUP_CERT` to absolute paths outside the checkout on the
signing computer. Verify the requested CN matches the reviewed identity; reject
unexpected subjects. Do not blindly sign CSRs from an untrusted source.

```sh
openssl req -in "$BACKUP_CSR" -noout -verify -subject -nameopt RFC2253
# Require at least 90 days of CA validity before issuing a 90-day leaf.
openssl x509 -in "$BACKUP_CA_DIR/ca.crt" -noout -checkend 7776000 || exit 1
test ! -e "$BACKUP_CERT" || exit 1
openssl x509 -req -sha256 -days 90 -in "$BACKUP_CSR" \
  -CA "$BACKUP_CA_DIR/ca.crt" -CAkey "$BACKUP_CA_DIR/ca.key" \
  -set_serial "0x$(openssl rand -hex 16)" \
  -extfile config/environments/aws/staging/homelab-recovery/openssl.cnf \
  -extensions client_extensions -out "$BACKUP_CERT"
openssl verify -purpose sslclient -CAfile "$BACKUP_CA_DIR/ca.crt" "$BACKUP_CERT"
```

Return `client.crt` and public `ca.crt` to the execution host. Verify the chain and
that the certificate's public key matches the local leaf key before activation:

```sh
openssl verify -purpose sslclient -CAfile "$BACKUP_CLIENT_DIR/ca.crt" \
  "$BACKUP_CLIENT_DIR/client.crt"
openssl x509 -in "$BACKUP_CLIENT_DIR/client.crt" -pubkey -noout | openssl sha256
openssl pkey -in "$BACKUP_CLIENT_DIR/client.key" -pubout | openssl sha256
```

The two hashes must match. Record subject, serial, SHA-256 fingerprint and expiry,
not key contents. Schedule renewal at day 60; alert if fewer than 30 days remain:
`openssl x509 -in "$BACKUP_CLIENT_DIR/client.crt" -noout -checkend 2592000`.
This PR does not install that monitoring or a renewal scheduler.

## 4. Review and deploy the AWS identity

First set `create_backup_identity = true` in the reviewed environment tfvars.
From the repository root on the administration computer:

```sh
export TF_VAR_backup_ca_certificate_pem="$(cat "$BACKUP_CA_DIR/ca.crt")"
./scripts/infra.sh aws-staging-homelab-recovery init
./scripts/infra.sh aws-staging-homelab-recovery validate
./scripts/infra.sh aws-staging-homelab-recovery plan
# After review, apply with the same public CA input:
./scripts/infra.sh aws-staging-homelab-recovery apply
unset TF_VAR_backup_ca_certificate_pem
```

Read `backup_trust_anchor_arn`, `backup_profile_arn`, `backup_upload_role_arn` and
`bucket_name` via `tofu -chdir=live/aws/staging/workloads/homelab-recovery output`.
These identifiers are public recovery coordinates. Save them with the reviewed
Git revision independently of the execution host.

## 5. Configure the uploader

Install the official `aws_signing_helper` release **1.8.5**, verifying the
platform-specific SHA-256 checksum from the [AWS download table](https://docs.aws.amazon.com/rolesanywhere/latest/userguide/credential-helper.html).
For Linux x86-64 the pinned download is
`https://rolesanywhere.amazonaws.com/releases/1.8.5/X86_64/Linux/Amzn2023/aws_signing_helper`,
SHA-256 `beec9ed1c492d93db809890f16713e3556353294b823c2184ad4e891f1b2b54d`.
For another platform select its matching binary and preserve that checksum.

Add a dedicated AWS config profile; replace every placeholder with the outputs
and absolute execution-host paths. Keep the `credential_process` on one line.

```ini
[profile homelab-backup-upload]
region = us-east-1
credential_process = /ABSOLUTE/PATH/aws_signing_helper credential-process --certificate /ABSOLUTE/PATH/client.crt --private-key /ABSOLUTE/PATH/client.key --trust-anchor-arn TRUST_ANCHOR_ARN --profile-arn PROFILE_ARN --role-arn UPLOAD_ROLE_ARN --session-duration 3600
```

Run `aws --profile homelab-backup-upload sts get-caller-identity` and verify the
account and assumed role. Do not invoke the credential process directly into logs:
its output contains temporary AWS credentials. Ensure ambient AWS credential
variables are unset and no static keys exist for this profile before testing.

Before accepting enrollment, prove: a non-sensitive canary upload under
`routine/` succeeds; the restore login downloads it and matches its checksum;
uploader GetObject/DeleteObject and upload outside the three allowed prefixes
return AccessDenied; a certificate with the wrong CN cannot obtain a session.
Use disposable canaries, never live backup objects, for denied-operation tests.
Object Lock retains uploaded canary versions for at least 30 days. These live tests
are pending deployment, not replaced by OpenTofu mock tests.

## Renewal, loss and compromise

Routine renewal: generate a new key/CSR in a new execution-host directory, sign
for 90 days, verify, then switch the profile paths and test. Reusing the same CN
permits both certificates until expiry; this is renewal, **not revocation**.

Lost/compromised leaf: disable new sessions by setting
`backup_identity_enabled = false` and applying. For an urgent incident, disable
the `homelab-backup-upload` profile in the AWS Roles Anywhere console immediately,
then reconcile desired state. Existing STS credentials may remain valid for up to
one hour; disabling a profile does not revoke them. Use IAM's **Revoke active
sessions** action on the upload role if existing sessions must be cut off too.

Issue a fresh key/certificate with a new CN (for example
`homelab-backup-uploader-02`), change the tfvars CN and re-enable the identity in a
reviewed apply. Verify the new identity succeeds and the old CN fails to obtain
credentials. This implementation revokes the whole uploader identity by changing
its allowed CN; it does not register a CRL or support per-serial revocation.

CA compromise: disable sessions, replace the CA and trust-anchor certificate,
issue a fresh client identity, and verify the old chain fails. Never re-enable a
compromised CA. Preserve public audit evidence; replace compromised secrets.

## Independent restore access

The restore policy remains separate from the certificate uploader. Before declaring
DR ready, verify the operator-selected existing AWS administrator login (`admin` profile) from a clean machine can list versions, GetObjectVersion and decrypt
with KMS, without the uploader key, signing CA, Talos or Tailscale. Preserve MFA and
account-recovery access outside the failed devices. Client-side backup decryption
keys are separate and also need independent custody. No new human principal is
assumed or granted access by this PR.
