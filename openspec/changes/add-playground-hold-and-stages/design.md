## Context

The coordinator treats a `homelab-platform` Lease labelled `homelab.tfdraw.dev/power-hold=true` with `hosts` covering `primary` as demand until the label is turned off (`coordinator.py`, "Durable CI hold"). CI creates one per run through `scripts/homelab-power-hold.py`. The lifecycle controller stops the runtime on its own after `idleTimeoutSeconds` of verified idle (`state.py::Observation.reconcile`) and knows nothing about holds.

Measured on the worker (2026-09-27): Ollama's `/api/ps` lists a model only once its weights are loaded (the 27B appeared at 17 s of an 18.7 s first-byte wait from page cache; 60 to 75 s from disk). The final chunk of every answer carries `load_duration`, `prompt_eval_count`, `prompt_eval_duration`, `eval_count`, `eval_duration`. The kubelet stats summary reports the runtime pod's working set live (17.8 GiB with the 27B loaded).

## Decisions

- **One fixed lease, owned by the chart.** `homelab-always-on` renders `host-hold-playground` in `homelab-platform` with the label `false`. The gateway only needs `get` and `patch` on that one name, so the Role is bound by `resourceNames`. The lease does not become a new coordinator concept: to the coordinator it is one more durable hold. A management dispatch resets the label to `false`, which is the right outcome for a maintenance window.
- **Expiry lives in the gateway**, not the coordinator. The coordinator deliberately never expires holds (a killed CI runner must not lose protection). The gateway stamps `homelab.tfdraw.dev/hold-until` when it sets the hold and its 5 s heartbeat turns the label off once that passes. Cap 12 hours. If the gateway is down the hold stays until it returns, which is the safe direction.
- **Page on the gateway at `/_power/`**, not inside Open WebUI. It works when the UI is down, costs nothing on the phone, and Open WebUI has no route under `/_power/`. Only tailnet devices reach it, the same trust as waking the host. Form posts are accepted only from the same origin (`Sec-Fetch-Site`), and the two endpoints never touch the application.
- **Runtime follows the host.** The lifecycle controller reads the lease each tick (one `get`, `optional`) and passes `held` into `reconcile`, which then never counts idle time. Status shows `hold_until`. Without the lease (chart not yet dispatched) nothing is held. Open WebUI keep-alive for the model is Ollama's own 5 minutes; a held runtime that unloads its model reloads from page cache in about 17 s, so the hold does not pin the model.
- **Wait stage signals, cheapest first.** Runtime pod not ready: `runtime starting` (existing `pods` permission). Model absent from `/api/ps`: `loading weights` with the runtime pod's working set from the kubelet stats summary against the catalog's weight size. Model present: `processing prompt` with a token estimate (`len(body) / 4`) at the last measured prompt rate. The stats summary needs `get` on `nodes/proxy` for the one worker; that also exposes read-only kubelet endpoints for that node (pod list, logs), accepted for a single homelab worker.
- **Learned timings** go in a new catalog table keyed by model and backend: last load seconds (only when Ollama reports a load over 1 s, so warm answers do not overwrite), prompt and generation tokens per second. Shown as "~1:05 typical for this model" once known; before that the line says so rather than guessing.

## Risks

A hold set from a lost phone runs the host for up to 12 hours. The page shows the release time and the Release button works from any tailnet device. The kubelet stats read is best effort: when it fails the loading line drops the memory figure rather than the stage.
