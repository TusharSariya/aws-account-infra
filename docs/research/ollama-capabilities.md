# Ollama capabilities for Hugging Face pull, context and KV quantisation

Research updated: 2026-09-26. Supports [Research Ollama capabilities for Hugging Face pull, context and KV quantisation](https://github.com/TusharSariyaOrg/aws-account-infra/issues/241), a child of the model playground map [#237](https://github.com/TusharSariyaOrg/aws-account-infra/issues/237). Documentation, source and live-registry review only; no cluster changes. Source citations are to the pinned Ollama tag `v0.34.0` unless a `main` link is stated, and upstream `main`/`master` links are moving references.

## Pinned version

`config/environments/kubernetes/homelab/ollama-values.yaml` on `main` pins `ollama/ollama@sha256:684d8674b4315fa18f4f0e973a118ec2652ed96f67563277839985175858e0ba`. The Docker Hub tag API maps that digest to tag **`0.34.0`** (pushed 2026-09-09). The GitHub release `v0.34.0` is dated 2026-09-05; later releases at the time of writing are `v0.34.1` (09-14), `v0.34.2` (09-15), `v0.34.3` (09-19), `v0.34.4` (09-23) and pre-release `v0.40.0-rc0` (09-25). Ollama 0.34.0 builds llama.cpp at tag `b10760` (`LLAMA_CPP_VERSION`). Sources: [Docker Hub tags API](https://hub.docker.com/v2/repositories/ollama/ollama/tags), [GitHub releases](https://github.com/ollama/ollama/releases), [LLAMA_CPP_VERSION](https://github.com/ollama/ollama/blob/v0.34.0/LLAMA_CPP_VERSION).

## Recommendation

The pinned 0.34.0 supports everything the map needs: `hf.co/user/repo:QUANT` pulls, per-request `num_ctx`, `OLLAMA_KV_CACHE_TYPE=q8_0` with flash attention, `/api/tags`, `/api/ps` with `context_length`, streamed `/api/pull` progress, and the OpenAI-compatible surface. Two things need care in the spec:

1. **Private or gated Hugging Face repos must be addressed as `huggingface.co/...`, not `hf.co/...`, and the Ollama SSH public key must be registered on the Hugging Face account.** Ollama authenticates to registries only by signing a challenge with its `id_ed25519` key; there is no token environment variable or API field. Hugging Face answers gated repos with a `Basic realm="https://huggingface.co/api/models/<repo>/ssh-auth"` challenge, and 0.34.0 rejects that realm when the request host was `hf.co` (open upstream issue #15661, unmerged PR #16180, still present on `main`). Public repos work under either host.
2. **Changing `num_ctx` reloads the model.** The scheduler compares the effective `num_ctx` of the running runner with the request and tears the runner down on mismatch, so a per-chat context selector costs a full reload on every change. Prefer a small set of context presets, or set context per model with `ollama create` and treat each preset as its own catalog entry.

Bumping to 0.34.3 or later is worthwhile but not required: 0.34.1 makes `/api/tags` about ten times faster on large libraries and reports `capabilities` consistently; 0.34.3 restores cross-host redirects among an allowlist (`ollama.com`, `ollama.ai`, `hf.co`, `huggingface.co`) after a 0.34.2 regression that broke Hugging Face CDN redirects. Nothing in 0.34.1 to 0.34.4 changes context, KV cache, scheduler or offload behaviour.

## Pulling GGUF from Hugging Face

The Hugging Face integration documents `ollama run hf.co/{username}/{repository}` and `hf.co/{username}/{repository}:{quantization}`; `hf.co` and `huggingface.co` are both accepted, the quant tag is case-insensitive, a full filename works as a tag, and with no tag `Q4_K_M` is chosen when present, else "one reasonable quant type present inside the repo". Chat template, system prompt and sampling parameters can be overridden by `template`, `system` and `params` files in the repo. [Hugging Face Ollama docs](https://huggingface.co/docs/hub/en/ollama)

The same page documents private repos: copy `~/.ollama/id_ed25519.pub` and add it under the Hugging Face account's SSH keys. This is the only credential path. In 0.34.0 the pull handler builds `registryOptions{Insecure: req.Insecure}` and nothing else, and a 401 challenge is answered by `getAuthorizationToken`, which signs the realm URL with the Ollama key and sends the signature as the `Authorization` header. There is no Hugging Face token variable in `envconfig`. Sources: [routes.go PullHandler](https://github.com/ollama/ollama/blob/v0.34.0/server/routes.go), [auth.go getAuthorizationToken](https://github.com/ollama/ollama/blob/v0.34.0/server/auth.go), [envconfig/config.go](https://github.com/ollama/ollama/blob/v0.34.0/envconfig/config.go). A Hugging Face discussion on a gated Gemma GGUF confirms the 401 clears once the SSH key is added. [google/gemma-3-27b-it-qat-q4_0-gguf discussion 2](https://huggingface.co/google/gemma-3-27b-it-qat-q4_0-gguf/discussions/2)

Live probe on 2026-09-26 with Ollama's User-Agent: `https://hf.co/v2/<repo>/manifests/latest` returns `307` to `https://huggingface.co/...`; a public repo on `huggingface.co` returns `200` with no challenge; a gated repo returns `401 WWW-Authenticate: Basic realm="https://huggingface.co/api/models/<repo>/ssh-auth"` from both hosts. `getAuthorizationToken` refuses when `redirectURL.Host != originalHost`, and `originalHost` is the host of the URL the client requested, so `hf.co/...` fails on gated or private repos with `realm host "huggingface.co" does not match original host "hf.co"` while `huggingface.co/...` succeeds. Upstream tracks this as [issue #15661](https://github.com/ollama/ollama/issues/15661) (open) and [PR #16180](https://github.com/ollama/ollama/pull/16180) (unmerged); `main`'s `auth.go` still has the strict check. Public pulls are unaffected because no challenge is issued and the Go HTTP client follows the 307 by default (`CheckRedirect` is nil in the pull path in 0.34.0).

Gated repos additionally require the account to have accepted the model licence on the Hugging Face site; Ollama has no flow for that. Ollama caches the pulled model under its own store; re-pulling the same `hf.co` name is a no-op when the manifest digest is unchanged.

## Context length

Three layers, lowest wins: a request `options.num_ctx`, a model parameter (`PARAMETER num_ctx` in a Modelfile, or `params` in the Hugging Face repo), then the server default. If none is set, 0.34.0 picks the default by total VRAM at startup: `>= 47 GiB` gives 262144, `>= 23 GiB` gives 32768, else 4096. `OLLAMA_CONTEXT_LENGTH` replaces that tier logic with a fixed value. The pinned FAQ still says "By default, Ollama uses a context window size of 4096 tokens"; the code and the `envconfig` help text ("default: 4k/32k/256k based on VRAM") are authoritative. On the CPU worker (no GPU) and on an 8 GiB RTX 3060 Ti the tier default is 4096. Sources: [routes.go usesAutomaticNumCtx and VRAM tiers](https://github.com/ollama/ollama/blob/v0.34.0/server/routes.go), [FAQ](https://github.com/ollama/ollama/blob/v0.34.0/docs/faq.mdx), [Modelfile parameters](https://github.com/ollama/ollama/blob/v0.34.0/docs/modelfile.mdx), [context length page](https://docs.ollama.com/context-length).

A request above the model's training context is clamped with a warning (`requested context size too large for model`). The training context is available as `model_info` in `/api/show`. [llm/server.go NewLlamaServer](https://github.com/ollama/ollama/blob/v0.34.0/llm/server.go)

**Changing `num_ctx` reloads.** `runnerRef.needsReload` compares the effective `NumCtx` of the loaded runner with the request; only when both are automatic (neither request nor model set `num_ctx`) is the existing value reused. A mismatch marks the runner for expiry and a new runner is started with the new context. The same applies to `num_batch`, adapters and projectors. [sched.go needsReload](https://github.com/ollama/ollama/blob/v0.34.0/server/sched.go)

If an automatic-context load fails with an out-of-memory error, the scheduler retries once at the next lower tier (256k to 32k to 4k); it does not do this for an explicit `num_ctx`. [sched.go reduceAutoNumCtxForLoadOOM](https://github.com/ollama/ollama/blob/v0.34.0/server/sched.go)

## KV cache quantisation and flash attention

`OLLAMA_KV_CACHE_TYPE` is a global server setting (`f16` default, `q8_0` about half the memory, `q4_0` about a quarter) and "requires Flash Attention". It is per server, not per model or request: "Currently this is a global option - meaning all models will run with the specified quantization type." So the map's open question "per-chat KV cache quantisation choice versus a global setting" is answered by the runtime: only global is possible without running a second Ollama instance. Sources: [FAQ](https://github.com/ollama/ollama/blob/v0.34.0/docs/faq.mdx), [docs.ollama.com FAQ](https://docs.ollama.com/faq).

0.34.0 passes the value straight to llama-server as `--cache-type-k` and `--cache-type-v`, and passes `--flash-attn on|off|auto`: `on` or `off` when `OLLAMA_FLASH_ATTENTION` is set, otherwise `auto` if every device reports support (CPU, Metal, supported CUDA, ROCm, Vulkan) and `off` if not. Ollama itself does no validation of the pair. llama.cpp `b10760` throws `quantized V cache was requested, but this requires Flash Attention` when flash attention resolves to off, and in `auto` mode a device probe can silently set it to off. Therefore set `OLLAMA_FLASH_ATTENTION=1` explicitly alongside `OLLAMA_KV_CACHE_TYPE=q8_0`, and verify on the Ivy Bridge worker (no AVX2) that the CPU flash attention path loads before relying on it. Sources: [llm/llama_server.go LlamaServerFlashAttention](https://github.com/ollama/ollama/blob/v0.34.0/llm/llama_server.go), [ml/device.go FlashAttentionSupported](https://github.com/ollama/ollama/blob/v0.34.0/ml/device.go), [llama-context.cpp at b10760](https://github.com/ggml-org/llama.cpp/blob/b10760/src/llama-context.cpp), [llama-server README at b10760](https://github.com/ggml-org/llama.cpp/blob/b10760/tools/server/README.md).

## Loaded models, parallelism and keep-alive

- `OLLAMA_MAX_LOADED_MODELS`: default 0, resolved at load time to `3 * max(GPU count, 1)`. When the count is reached, or the predicted memory of a new model exceeds 80 percent of free memory while other models are loaded, an idle runner is chosen and expired before the new load. The map's "one loaded model at a time" needs `OLLAMA_MAX_LOADED_MODELS=1` set explicitly. [sched.go processPending](https://github.com/ollama/ollama/blob/v0.34.0/server/sched.go), [FAQ concurrency](https://github.com/ollama/ollama/blob/v0.34.0/docs/faq.mdx)
- `OLLAMA_NUM_PARALLEL`: default 1. The KV allocation scales by `num_ctx * num_parallel`; embedding models and some architectures (`mllama`, `qwen3vl`, `qwen35`, `nemotron_h`, `lfm2` families and others) are forced to 1. [envconfig](https://github.com/ollama/ollama/blob/v0.34.0/envconfig/config.go), [sched.go load](https://github.com/ollama/ollama/blob/v0.34.0/server/sched.go)
- `OLLAMA_MAX_QUEUE`: default 512; beyond it the server returns 503.
- Keep-alive: `OLLAMA_KEEP_ALIVE` (default `5m`) sets the server default; a request `keep_alive` overrides it and accepts a duration string, a number of seconds, a negative value (keep loaded indefinitely) or `0` (unload after the response). An empty-prompt `/api/generate` or empty-messages `/api/chat` with `keep_alive: 0` unloads immediately, and the same without `keep_alive` preloads. The timer starts when the runner goes idle and resets on each request; `/api/ps` reports the resulting `expires_at`. [FAQ keep-alive](https://github.com/ollama/ollama/blob/v0.34.0/docs/faq.mdx), [api.md](https://github.com/ollama/ollama/blob/v0.34.0/docs/api.md), [sched.go expiry timers](https://github.com/ollama/ollama/blob/v0.34.0/server/sched.go)

Because the existing AI Pod wake gateway already applies a 30-minute idle shutdown, a `keep_alive` longer than 30 minutes is pointless on the server backend; `keep_alive: -1` on the desktop backend keeps a model resident until the router unloads it explicitly.

## API surface the router and UI will use

- `GET /api/tags`: `models[]` with `name`, `model`, `modified_at`, `size`, `digest`, `details{parent_model, format, family, families, parameter_size, quantization_level}` and `capabilities[]` (present in the 0.34.0 type, reported consistently from 0.34.1). Hugging Face pulls appear as `hf.co/user/repo:QUANT` names. [api/types.go ListModelResponse](https://github.com/ollama/ollama/blob/v0.34.0/api/types.go), [v0.34.1 release](https://github.com/ollama/ollama/releases/tag/v0.34.1)
- `GET /api/ps`: `models[]` with `name`, `model`, `size`, `digest`, `details`, `expires_at`, `size_vram` and `context_length`. `context_length` is in the 0.34.0 type even though the pinned `docs/api.md` example omits it; the current docs page lists it. The `ollama ps` processor column (`100% GPU`, `100% CPU`, `48%/52% CPU/GPU`) is derived from `size` and `size_vram`. [api/types.go ProcessModelResponse](https://github.com/ollama/ollama/blob/v0.34.0/api/types.go), [docs.ollama.com /api/ps](https://docs.ollama.com/api/ps)
- `POST /api/pull` with `{"model": "hf.co/user/repo:QUANT", "stream": true}` returns newline-delimited JSON: `{"status":"pulling manifest"}`, then per-layer `{"status":"pulling <digest>","digest":...,"total":...,"completed":...}` (`completed` may be absent until data arrives), then `verifying sha256 digest`, `writing manifest`, `removing any unused layers` (spelled `removing unused layers` in 0.34.0 code) and `success`. GGUF pulls use the per-layer path; the aggregate `pulling model` status with digest `sha256:model` is only used for safetensors (MLX tensor-layer) manifests. Cancelled pulls resume, and concurrent pulls of the same model share progress. Errors arrive as a final object with `error`. [api.md pull](https://github.com/ollama/ollama/blob/v0.34.0/docs/api.md), [images.go PullModel](https://github.com/ollama/ollama/blob/v0.34.0/server/images.go)
- `POST /api/show` returns `model_info` including the training context length, plus `capabilities`; from 0.34.3 it also advertises `thinking` levels and default. [v0.34.3 release](https://github.com/ollama/ollama/releases/tag/v0.34.3)
- OpenAI-compatible: `/v1/chat/completions` (streaming, JSON mode, vision by base64, tools, `reasoning_effort`; no `logprobs`, `tool_choice`, `logit_bias`, `n`), `/v1/completions`, `/v1/models`, `/v1/models/{model}`, `/v1/embeddings`, and stateless `/v1/responses`. The OpenAI surface has no context-size field; the documented route is `ollama create` with `PARAMETER num_ctx`. The native `/api/chat` is the only way to set `num_ctx` and `keep_alive` per request, so the router should speak `/api/chat` to backends and expose OpenAI shape to clients if needed. [openai-compatibility.mdx](https://github.com/ollama/ollama/blob/v0.34.0/docs/api/openai-compatibility.mdx)

## CPU offload when a model exceeds VRAM

0.34.0 does not pass `-ngl` unless `num_gpu` is set explicitly (`num_gpu: 0` forces CPU-only); by default llama-server's `--gpu-layers auto` places as many layers as fit in VRAM and the remainder on the CPU, so an oversized model on the RTX 3060 Ti loads with a CPU/GPU split rather than failing. Ollama predicts VRAM before spawning and, if other models are loaded and the prediction exceeds 80 percent of free memory, evicts first; the first model on an empty server is loaded without that gate. Layer placement is read back from llama-server's `offloaded N/M layers to GPU` log line and surfaces as `size_vram` in `/api/ps`. Multimodal projectors are kept on CPU during partial offload. Sources: [llm/llama_server.go launch params and offloadedLayersRegex](https://github.com/ollama/ollama/blob/v0.34.0/llm/llama_server.go), [sched.go load](https://github.com/ollama/ollama/blob/v0.34.0/server/sched.go), [llama-server README at b10760](https://github.com/ggml-org/llama.cpp/blob/b10760/tools/server/README.md), [FAQ multi-GPU](https://github.com/ollama/ollama/blob/v0.34.0/docs/faq.mdx).

For the map's fit rule this means Ollama will not refuse an oversized model on the GPU host; the router must apply the declared budget itself if silent partial offload (and its speed penalty) is unwanted. `OLLAMA_GPU_OVERHEAD` reserves bytes per GPU from the prediction. An explicit `num_gpu` count of layers is honoured but also triggers a reload when changed.

## What the pinned 0.34.0 lacks

| Capability | 0.34.0 | Fixed or added in |
|---|---|---|
| Gated or private repo pull via `hf.co/...` host | Fails on realm host check; use `huggingface.co/...` | Not fixed on `main` (#15661 open, #16180 unmerged) |
| Cross-host redirect allowlist for HF CDN | Not needed: redirects followed by default | Regressed in 0.34.2, allowlist in 0.34.3 (#18533) |
| Fast `/api/tags` on large libraries, consistent `capabilities` | Slow (3.1 s cold on a large library), capabilities inconsistent | 0.34.1 |
| `/api/show` thinking levels and default | Absent | 0.34.3 |
| Per-request or per-model KV cache type | Global only | Not available in any release |
| `num_ctx` via OpenAI endpoints | Not available | Not available in any release |
| MLX default on Apple Silicon | n/a for this platform | 0.40.0-rc0 |

Everything else in the ticket's question (HF `:QUANT` tags, `num_ctx` per request and per model, VRAM-tier default context, `OLLAMA_KV_CACHE_TYPE` with flash attention, `OLLAMA_MAX_LOADED_MODELS`, `OLLAMA_NUM_PARALLEL`, keep-alive, `/api/tags`, `/api/ps` with `context_length`, streamed `/api/pull`, OpenAI endpoints including `/v1/responses`, automatic partial offload) is present in 0.34.0.
