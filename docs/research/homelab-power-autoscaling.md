# Homelab demand, node capacity, and physical power

Research updated: 2026-09-20. Supports [Investigate Kueue, Proxmox and physical-power autoscaling integration](https://github.com/TusharSariyaOrg/aws-account-infra/issues/104). Documentation and source review only; no live changes. Upstream `master`/`main` links are moving references, not version compatibility guarantees.

## Recommendation

The user now selects **disposable worker VMs created for demand and deleted after drain**, superseding the earlier retained-VM assumption. Durable application data is separate from disposable worker OS/scratch disks. This is a design decision, not permission to delete existing production VMs or their data.

The selected capacity model is **two fixed slots, each a node group with min=0/max=1**, one large main worker per physical host, sized after measuring the PVE reserve. There is no bootstrap worker and no predictive queue delay. A single 30-minute idle window gates worker deletion and physical-host shutdown; there is no second cooldown after deletion. New demand cancels shutdown before its irreversible boundary. These are user decisions.

Recommend prototyping **upstream CA + externalgrpc + a direct two-endpoint PVE/IMM2 adapter** for this fixed topology. Keep Kueue admission and Kubernetes placement upstream. CAPMOX now matches disposable create/delete semantics, but its unresolved independent-endpoint and laptop-control-plane ownership gates make it an alternative rather than the first implementation target. No PVE cluster merger is implied. The custom adapter still requires a careful lifecycle state machine; two slots bound the inventory but do not remove concurrency, storage, or shutdown obligations.

Both choices still need physical-host wake/shutdown and app activity integration. The adapter cost and controller footprint on the laptop remain unmeasured. Durable storage must be separated from worker ownership before any production deletion.

## Demand must survive zero workers

The repository baseline pins Kueue v0.19.4, enables Pod and Deployment integrations, and creates ARC runner Pods with a Kueue scheduling gate; ARC has zero minimum runners. The runner selector and queue ResourceFlavor currently constrain work to worker01. These are migration inputs, not changes made here. Sources: [Kueue values](../../config/environments/kubernetes/homelab-ci/kueue-values.yaml), [ARC values](../../config/environments/kubernetes/homelab-ci/arc-runner-values.yaml), [queue template](../../charts/homelab-queue/templates/queue.yaml).

Scheduling-gated Pods are intentionally excluded from scheduling; relying only on unschedulable Pods can miss demand while Kueue holds a gate. Once Kueue admits a workload without a capacity check, its ungated pending Pods can trigger ordinary CA scaling. The deadlock arises if admission itself waits for absent capacity without a wake signal. [Scheduling readiness](https://kubernetes.io/docs/concepts/scheduling-eviction/pod-scheduling-readiness/), [upstream explanation of CA exclusion](https://kubernetes.io/blog/2022/12/26/pod-scheduling-readiness-alpha/)

Kueue's ProvisioningRequest admission controller supplies PodTemplates from quota-reserved Workloads before their Pods are released. Configure it for all relevant CPU/RAM workloads; do not copy a GPU-only `managedResources` example. Quota describes approved potential capacity, not merely currently powered-on capacity; otherwise zero quota can prevent reservation and hence the provisioning request. This quota consequence follows from the documented ordering. [Kueue v0.19 ProvisioningRequest](https://kueue.sigs.k8s.io/v0.19/docs/concepts/admission_check/provisioning_request/)

**Choose the provisioning class deliberately.** `check-capacity.autoscaling.x-k8s.io` checks existing capacity; it does not itself wake nodes. `best-effort-atomic-scale-up.autoscaling.x-k8s.io` can request scale-up. CA documents support from 1.30.2, with ProvisioningRequest CRDs, RBAC and `--enable-provisioning-requests=true`. Its successful scale-up status is not a promise that the nodes and application are already Ready. CA also considers Pod relocation when removing capacity; fit constraints and eviction blockers can prevent removal. [CA FAQ](https://github.com/kubernetes/autoscaler/blob/master/cluster-autoscaler/FAQ.md)

The external gRPC implementation explicitly returns `ErrNotImplemented` for `AtomicIncreaseSize`. Therefore the best-effort class uses its non-atomic fallback; an external provider cannot advertise strict atomic batch allocation through the inspected interface. Treat node readiness, boot timeout and request expiry as separate integration checks, and retain queued work until runnable. [External gRPC implementation](https://github.com/kubernetes/autoscaler/blob/master/cluster-autoscaler/cloudprovider/externalgrpc/externalgrpc_node_group.go)

## Repository integration touchpoints

The current preflight insists on worker01 being Ready and filesystem measurements no older than 300 seconds. A sleeping host cannot satisfy those checks. Separate approved attainable capacity used to request a wake from fresh post-wake admission/storage validation; preserve CPU, RAM, disk and eviction-headroom bounds. Do not resolve zero-capacity startup by bypassing all budget checks. [Capacity verifier](../../scripts/kueue_capacity.py)

ARC controller and scale-set listeners, Kueue and CA must stay on the laptop management capacity: zero idle runner Pods does not eliminate the components that receive demand and create those Pods. Move their placement deliberately, remove the worker01-only selector where workloads are eligible for both hosts, and update workflow preflights consistently. This is a proposed placement requirement, not a live deployment claim. The existing runner definition is in [ARC values](../../config/environments/kubernetes/homelab-ci/arc-runner-values.yaml).

## Existing options and their fit

| Option | Verified capability | Gap for this design |
|---|---|---|
| CA + external gRPC | Upstream placement simulation/scaling with an out-of-tree provider; mTLS supported | Requires a create/delete PVE and IMM2 adapter; maintains our independent endpoint mapping |
| CA + Cluster API + CAPMOX | Scales MachineDeployments/MachineSets, provisions Proxmox machines | Lifecycle now fits; independent PVE endpoints, laptop control-plane ownership, version set and power integration unresolved |
| Standalone Talos/Proxmox autoscalers | Detect pending Pods and provision Talos workers through PVE | Create/destroy now fits, but reviewed implementations lack verified Kueue gate/IMM2 integration |
| Metal3 BareMetal Operator | Actual BMC-controlled physical power; can adopt externally provisioned machines | Additional operator/Ironic footprint; does not connect PVE guest lifecycle to queued work by itself |

The CA external gRPC provider exists specifically to separate cloud operations from CA without a fork. Its default RPC timeout is five seconds: record desired state and perform long boot operations asynchronously, rather than blocking an RPC for a server boot. Use authenticated communication. [External provider README](https://github.com/kubernetes/autoscaler/blob/master/cluster-autoscaler/cloudprovider/externalgrpc/README.md)

Cluster API scale-from-zero needs provider template capacity or explicit annotations for CPU, memory, labels, taints and other relevant resources. It is an available mechanism, not an assumption that a particular provider supports every detail. [CA Cluster API provider](https://github.com/kubernetes/autoscaler/blob/master/cluster-autoscaler/cloudprovider/clusterapi/README.md)

CAPMOX's deletion path calls VM deletion. That now matches disposable workers, subject to separating application data from owned guest disks. [CAPMOX deletion source](https://github.com/ionos-cloud/cluster-api-provider-proxmox/blob/main/internal/service/vmservice/delete.go)

Talos CAPI remains possible, but Sidero announced on August 19, 2026 that development and commercial support are moving to community maintenance. Do not describe it as either a currently Sidero-supported default or nonexistent software. The maintenance transition and version compatibility would need evaluation if selected. [Sidero announcement](https://www.siderolabs.com/blog/talos-linux-capi-community-maintenance)

Two concrete alternatives illustrate the mismatch. `shokohsc/talos-proxmox-autoscaler` documents unschedulable-Pod detection, PXE-created workers and descheduler-triggered destruction. `Pzharyuk/proxmox-autoscaler` documents creating Talos VMs, choosing the PVE node with the fewest autoscaled VMs, and stopping/destroying low-utilization workers. Their VM lifecycle now fits, but their documented operating model does not establish physical power-aware packing or Kueue admission integration. This is a feature comparison, not a security or quality audit. [shokohsc project](https://github.com/shokohsc/talos-proxmox-autoscaler), [Pzharyuk project](https://github.com/Pzharyuk/proxmox-autoscaler)

Metal3 can enroll preinstalled hosts with `externallyProvisioned: true` and control their power through `online`; its example supports an IPMI BMC. This is genuine physical-power functionality without requiring reinstallation. It remains a possible power backend, but adopting it alone does not solve PVE guest ownership, application drains, or Kueue demand. [Metal3 external hosts](https://book.metal3.io/bmo/externally_provisioned.html)

## CAPI viability gates for the actual topology

CAPMOX's current compatibility table lists v0.9 with CAPI v1.11/v1.12. Talos bootstrap's v0.7 alpha releases implement CAPI v1beta2: alpha.2 explicitly adds Talos 1.13, and alpha.3 adds the Talos 1.14 contract. This is evidence of a plausible version intersection, not a tested production bill of materials. Pin and test the entire version set before deployment; the newer contract release is a prerelease. [CAPMOX compatibility](https://github.com/ionos-cloud/cluster-api-provider-proxmox/blob/main/README.md), [Talos bootstrap releases](https://github.com/siderolabs/cluster-api-bootstrap-provider-talos/releases)

Talos bootstrap generates worker configuration via `TalosConfigTemplate` and a MachineDeployment/MachinePool. Its README says to install alongside the Talos control-plane provider; it does not establish automatic adoption of the existing laptop control plane. A worker-only setup needs the existing cluster CA/secrets, API endpoint, provider IDs, owner references and CAPI readiness contract established deliberately. A provider-maintainer Talos example exists, but is not proof for this mixed laptop/PVE ownership topology. [Talos bootstrap README](https://github.com/siderolabs/cluster-api-bootstrap-provider-talos), [CAPMOX Talos example](https://github.com/ionos-cloud/cluster-api-provider-proxmox/discussions/405)

The physical hosts are separate PVE installations, both currently named `pve`, not a confirmed Proxmox cluster. Current CAPMOX constructs one API client from the `url` in one `credentialsRef` Secret for a ProxmoxCluster. Therefore an `allowedNodes: [pve]` list addresses that endpoint's node namespace, not both independent hosts. Treat host identity as endpoint plus node name; duplicate names cannot be used as global identifiers. A supported multi-endpoint approach was not established in this bounded review. Creating two arbitrary CAPI Clusters aimed at one Kubernetes cluster is not assumed safe. [CAPMOX client construction](https://github.com/ionos-cloud/cluster-api-provider-proxmox/blob/main/pkg/scope/cluster.go)

CAPMOX's `zoneConfigs` describe network address pools/DNS, with credentials on the parent ProxmoxCluster. They do not demonstrate per-zone PVE API endpoints. Joining physical hosts into a new Proxmox cluster would be a separate architecture change with quorum and naming implications, not an incidental prerequisite to silently perform. [ProxmoxCluster schema](https://github.com/ionos-cloud/cluster-api-provider-proxmox/blob/main/api/v1alpha2/proxmoxcluster_types.go)

Templates also impose a wake dependency. The machine schema defines a source node/template and defaults to full clones; unspecified placement may distribute VMs across allowed nodes. Proposed policy: a versioned Talos template on each eligible standalone host, clone locally after that host wakes, so waking secondary never requires primary merely to supply an image. Keep template identity separate from disposable guest identity. Linked clones require preserving the backing template, whereas full clones trade copy cost for independence. The exact provisioning time and allocated disk cost need measurement. [Clone/template schema](https://github.com/ionos-cloud/cluster-api-provider-proxmox/blob/main/api/v1alpha2/proxmoxmachine_types.go)

The laptop must run the complete chosen controller set alongside DNS/control-plane services. CAPI adds its management controllers and provider controllers; the usage guide also initializes its dependencies. No controller-load measurement was made here, so the previous idle Talos prototype is not evidence that the full stack fits. [CAPMOX usage](https://github.com/ionos-cloud/cluster-api-provider-proxmox/blob/main/docs/Usage.md)

## Durable storage and replaceable identity

User intent makes worker OS/scratch disposable, not database files. Before migration, define data ownership, attachment and placement so worker deletion cannot delete application volumes. A Kubernetes PVC alone does not guarantee that: underlying storage and reclaim policy matter. Local PV node affinity can tie data to a deleted node; new hostnames require an explicit placement/reattachment design. This is a storage-lifecycle prerequisite, not the deferred backup/redundancy work. [Kubernetes persistent volumes](https://kubernetes.io/docs/concepts/storage/persistent-volumes/)

Give replacement nodes new identities and advertise durable capabilities through labels such as storage domain, hardware class and physical-host domain. Remove fixed worker01/worker02 hostname assumptions from Kueue flavors, runner selectors and preflight code where the workload is portable. Keep real data locality constraints rather than pretending all cattle workers are interchangeable. CA template labels must describe the replacement nodes accurately even at zero instances. [CA Cluster API scale-from-zero](https://github.com/kubernetes/autoscaler/blob/master/cluster-autoscaler/cloudprovider/clusterapi/README.md)

## Ordinary durable-volume attachment

The current primary app storage is local-path data on an XFS filesystem on the worker's 1200-GiB data disk (`/dev/sdb1`), supplied as session evidence by the parent investigation. This is not automatically an independently managed CSI volume. Retaining a PVC or filesystem mount path does not make deletion of that worker VM safe. The migration choice remains: transfer application data to independently owned volumes, or establish a reviewed ownership-transfer mechanism for the existing data disk. No in-place conversion is prescribed here.

**Detach is not retain across guest deletion.** Proxmox's documented unlink without force changes an attached disk to an `unused[n]` entry; unlinking an unused entry removes the physical image. Thus a detach-and-destroy recipe does not establish independent lifetime. The inspected documentation is an older maintainer source snapshot; exact installed-version API behavior must be checked read-only and proven on scratch disks before selecting operations. Do not hand-edit VM config, rename live volume files, or infer that an unused slot is protected. [Proxmox maintainer qm documentation source](https://github.com/ThomasLamprecht/pve-docs/blob/master/qm.1-synopsis.adoc)

The Proxmox CSI project is a relevant candidate: it explicitly supports multiple independent Proxmox clusters, allocates PVs on the hypervisor, and reattaches them between Kubernetes VMs on the same physical host. Local storage cannot automatically migrate between physical hosts. Crucially, its README requires clustered Proxmox nodes, while allowing a one-node cluster. Two unique region names with zone `pve` can distinguish the two endpoints, but compatibility with the currently standalone installations remains a prerequisite to verify, not a fact established by this review. This does not require joining the two hosts to each other. [CSI project contract](https://github.com/sergelogvinov/proxmox-csi-plugin)

The CSI controller selects an endpoint by region, allocates a volume using its configured controller VMID rather than the consuming worker's VMID, and implements publish/unpublish with detach completion waiting. This establishes a purposeful independent-volume model, but does not prove that deleting a worker while its CSI volume remains attached is safe. The power adapter must wait for unmount/detach and inspect the guest's remaining disk references before deletion. Never interpret node deletion alone as storage detachment. [CSI controller source](https://github.com/sergelogvinov/proxmox-csi-plugin/blob/main/pkg/csi/controller.go)

Use an explicit retained data StorageClass/PV lifecycle if selected; the driver documents `Retain` and its `csi.proxmox.sinextra.dev/lifecycle: keep` option. Those control volume/PVC lifecycle, not physical-node readiness or forced VM deletion. Existing local-path directories require planned data migration; do not change a PVC's class and expect data movement. [CSI storage options](https://github.com/sergelogvinov/proxmox-csi-plugin/blob/main/docs/options.md)

## IaC and runtime ownership boundary

Proposed ownership: OpenTofu/Helm own fixed inventory, host/template/storage policy, reviewed per-host budgets, controller installation and permissions. The runtime adapter alone owns disposable worker VM instances and their OS/scratch disks; CSI, if selected, owns attachment and PV volumes under a separate retained-data policy. Do not have OpenTofu continuously reconcile the same worker instance as the autoscaler. Configuration and credentials stay reviewable; ordinary runtime create/delete follows the approved policy. App-specific restart, persistence and drain rules still determine eligibility.

## Packing and per-application permissions

Use accurate resource requests and a bin-packing scheduler profile such as `MostAllocated` for eligible workloads. That prefers existing high allocation; it does not move existing Pods or override storage/affinity constraints. [Kubernetes bin packing](https://kubernetes.io/docs/concepts/scheduling-eviction/resource-bin-packing/)

CA consolidation can reuse Kubernetes eviction semantics, but app policy must decide whether a workload is movable now. App configuration owns restart permission, active sessions, completion and storage constraints. PodDisruptionBudgets bound simultaneous voluntary disruption; they are not an activity detector and do not express the whole agreed lifecycle policy. [Disruption budgets](https://kubernetes.io/docs/tasks/run-application/configure-pdb/)

Proposed implementation boundary: app policy projects keep-awake and eviction eligibility into controller-visible state and Kubernetes constraints. Scheduled, on-invoke, persistent and experimental classifications remain app configuration. A persistent workload keeps its selected host awake; experimental work does not block ordinary shutdown, with graceful termination first. This paragraph records user decisions, not upstream behavior.

For two unequal workers, model one node group per physical host with minimum zero and maximum one, templates reflecting the fixed main-worker size, actual allocatable capacity and storage labels. Prefer capacity already awake, then one eligible host. Avoid balancing equivalent node groups if the objective is consolidation. Merely enabling CA does not guarantee a globally minimum-power placement or cancel an in-flight drain. Physical power state, draining targets and shutdown cancellation require explicit adapter/controller state. This is design inference from the distinct scheduling and infrastructure interfaces, not a promised CA feature. [Node autoscaling boundaries](https://kubernetes.io/docs/concepts/cluster-administration/node-autoscaling/)

## Physical lifecycle and the next bounded proof

Existing IMM2 research identifies SSH CLI and IPMI, not an assumed Redfish endpoint. IMM2 `power on` supplies the final wake operation. Its soft power-off option may force power off after its timeout, so it cannot replace app/Pod drain, guest shutdown and orderly PVE shutdown. Verify off through IMM2 after that sequence. [Existing IMM2 research](imm2-official-interfaces.md), [Lenovo power command](https://pubs.lenovo.com/imm2/aj1camst04)

Remaining bounded prototype contracts, without production migration or failure drills:

1. **Slot ownership:** one generation per host at most, stable group identity plus new VM/node identity each generation, idempotent create/delete after controller restart, and no effects on unmanaged resources. Fixed size leaves measured PVE reserve.
2. **Demand:** a zero-worker Kueue ProvisioningRequest selects an eligible slot without a bootstrap worker or prediction delay. Accurate template labels include storage domain; ordinary pending Pods work too. An unsatisfiable workload remains queued rather than causing repeated boots.
3. **Data lifetime:** on a small scratch PV, write a marker, gracefully stop its app, verify unmount and completed detach, delete the worker and its owned OS/scratch disks, create a replacement on the same host, reattach and read the marker. Verify unique endpoint/region mapping despite both PVE node names being `pve`. Establish CSI prerequisites first, without silently creating clusters.
4. **Deletion boundary:** prove attached or unused retained-data references block VM deletion, and PVC/data deletion is never inferred from worker idleness. Preserve data while all workers and physical hosts sleep.
5. **Consolidation and power:** app-permitted movement only; finish active CI. One shared 30-minute idle window then drain, detach, delete guest, orderly PVE shutdown and IMM2 verification. Demand arriving before committed shutdown cancels it; afterward it remains queued for wake. Adapter operations are asynchronous and serialized per host.
6. **IaC:** an ordinary OpenTofu plan does not recreate a worker intentionally removed by autoscaling or delete its retained data; Helm upgrades preserve the runtime ownership contract. Measure the full always-on controller set on the laptop.

These are ordinary lifecycle integration checks. Backup/restore, hardware-failure drills, redundancy and provider-outage work remain deferred by the user.
