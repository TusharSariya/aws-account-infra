**Verdict**

The platform is a carefully engineered *single-worker batch appliance* rather than a workload platform. Kueue, CEL admission, digest pinning, and the power coordinator are well done, but every workload class the operator wants beyond "bounded CPU batch on worker-01" is either missing or contradicted by the design: there is no always-on application tier (both workers auto-sleep after 300 s and the only awake node is a 2 vCPU/5 GiB laptop VM), GPU is explicitly out of scope and structurally blocked by Kueue's resource coverage, latency-sensitive and batch work share one flavor with equal priority and no preemption, and heterogeneous nodes require code edits in at least six places. Deployment is split across three mechanisms with an idle Argo CD. The bespoke Python control plane (~28k lines across 313 files) is the main long-term maintenance risk for a solo operator.

**Findings**

**F1 — Severity: High.** Claim: there is no persistent application tier; "persistent" apps are quiescible and the only always-on node is a 2 vCPU/5 GiB VM.
Evidence: `platform/automatic-power/README.md:3` ("automatic mode with a 300-second idle threshold"); `controllers/homelab-capacity/src/homelab_capacity/policy.py:16-40` lists nexus, nexus-postgres, cnpg, local-path, monitoring and all Argo CD components as `PLATFORM` (quiescible); `config/environments/kubernetes/homelab/lifecycle-values.yaml:3` `idleTimeoutSeconds: 300`; `platform/main-control-plane/vm.json` `"vcpus": 2, "memory_gib": 5`; `kubernetes/platform/main/placement/plan.py:16-23,26-41` moves kueue, argo, ARC, pihole, tailscale, ai-lifecycle onto the tainted control plane. Status: IMPLEMENTED-BUT-FLAWED. Failure scenario: a public or private app with a database is deployed as a Deployment on worker-01; after 5 idle minutes the host powers off, PostgreSQL and the app vanish, and the next request hits a cold 503 (F4) until a physical server boots. Any attempt to make it always-on lands on the 5 GiB laptop VM already hosting etcd, API server, CoreDNS, Cilium, kube-proxy, Kueue, Argo WF, ARC, Tailscale proxies and pihole. Fix: define an explicit always-on worker class (a small third node or a non-retained VM) with its own ResourceFlavor and node label, and make `policy.py` classify per-app via annotation (`homelab/quiescible: "false"`) instead of a hard-coded PLATFORM set. Confidence: High.

**F2 — Severity: High.** Claim: GPU workloads cannot be admitted at all; the design defers GPU to a non-cluster Ubuntu box.
Evidence: `charts/homelab-queue/templates/queue.yaml:49` `coveredResources: [cpu, memory, ephemeral-storage]`; `config/environments/kubernetes/homelab-ci/kueue-values.yaml:23-24` `excludeResourcePrefixes: []` (so a pod requesting `nvidia.com/gpu` is inadmissible in the ClusterQueue); `charts/homelab-queue/templates/admission.yaml:65-75` sums only those three resources; `docs/plans/talos-system-extensions.md:86-87` "NVIDIA extensions: the GPU remains attached to the conventional Ubuntu GPU worker"; `docs/plans/talos-kubernetes-rebuild.md:182` "external Ubuntu GPU worker lifecycle is deferred". No device plugin, RuntimeClass, NFD, or GPU flavor exists anywhere under `charts/`, `live/`, `config/`. Status: MISSING (PLANNED-ONLY for the Ubuntu join). Failure scenario: the operator adds a GPU pod in `homelab-models`; Kueue marks the Workload inadmissible ("resource nvidia.com/gpu not in ClusterQueue"), it stays gated forever, and the VAP would still pass. Fix: add a `gpu` ResourceFlavor with `nvidia.com/gpu` quota, extend `coveredResources`, add a GPU Talos schematic (nonfree-kmod-nvidia + nvidia-container-toolkit) or finish the Ubuntu join, plus a `nvidia` RuntimeClass and a GPU node taint/toleration. Confidence: High.

**F3 — Severity: High.** Claim: AI and CI serialize on one node with no priority, preemption, or real overflow, so interactive AI stalls CI and vice versa.
Evidence: `charts/homelab-ai/values.yaml:2-3` (ollama 29.5 CPU, "other three containers request 1.75 CPU" = 31.25) equals the entire pool `config/environments/kubernetes/homelab-ci/pool-values.yaml:2` `cpu: '31.25'`; `pool-values.yaml:8` `StrictFIFO`; `queue.yaml:45-47` `withinClusterQueue: Never`; `queue.yaml:71-73` a single WorkloadPriorityClass `value: 0`; `admission.yaml:60` forbids any `priorityClassName`; `config/environments/kubernetes/homelab-ci/arc-runner-values.yaml:29` runners have `nodeSelector: {kubernetes.io/hostname: talos-worker-01}`, which conflicts with the `homelab-secondary` flavor's `nodeLabels` (`queue.yaml:21`), so Kueue never assigns real runners to worker-02. The "overflow" evidence used synthetic pods (`platform/automatic-power/evidence-20260922.md:39`). Status: IMPLEMENTED-BUT-FLAWED. Failure scenario: a chat wakes `ai-runtime` while two runners hold 8 CPU; the AI Workload cannot fit, sits at the StrictFIFO head, and blocks every newer runner until the runners finish; once AI is up, zero CPU remains for CI for at least 300 s of idle. Fix: give runners a `stateless-compute` selector instead of a hostname; use `BestEffortFIFO`; add distinct WorkloadPriorityClasses (interactive > batch) with `withinClusterQueue: LowerPriority`; reduce ollama to leave headroom or split AI into its own ClusterQueue/cohort. Confidence: High.

**F4 — Severity: Medium.** Claim: cold requests return 503 rather than being held, so wake latency is exposed to users and public clients.
Evidence: `controllers/homelab-capacity/src/homelab_capacity/gateway.py:233-243` returns `503 "Starting the application server. Retry in 10 seconds. Your request has not been replayed."`. Wake includes IMM power-on, Proxmox boot, Talos boot and Nexus recovery (`README.md:26-28`, `evidence-20260922.md:35-37`). Status: IMPLEMENTED-BUT-FLAWED. Failure scenario: a browser or API client without retry logic (webhooks, mobile apps) fails outright for several minutes. Fix: hold the connection with a bounded wait (e.g. 120 s) and stream a progress page, or front public routes with a queueing proxy; return `Retry-After`. Confidence: High.

**F5 — Severity: Medium.** Claim: adding a heterogeneous worker requires editing code, not configuration, and batch placement prefers the same node as stateful/latency work.
Evidence: hostnames hard-coded in `charts/homelab-queue/templates/queue.yaml:21`, `policy.py:9`, `controllers/.../kueue.py:7`, `config/environments/talos/homelab/local-path-values.yaml:12-15`, `kubernetes/platform/main/placement/plan.py:13-14`; `kubernetes/platform/main/placement/compute-template.yaml:6-13` weights batch onto `worker-role: primary`, the node that also holds PostgreSQL, Nexus, monitoring and AI. Status: IMPLEMENTED-BUT-FLAWED. Failure scenario: a GPU server is added; Kueue flavors, the coordinator's FLAVORS map, the policy NODES map, and the post-renderer all need synchronized edits or the coordinator raises "Unregistered resource flavor" (`kueue.py:29`) and stops acking admission for everyone. Fix: drive flavors and host maps from a single `nodes.json` consumed by chart values, coordinator config and placement; invert the compute preference toward the secondary/batch role. Confidence: High.

**F6 — Severity: Medium.** Claim: talos-worker-02's machine configuration is outside IaC.
Evidence: `live/talos/homelab/main.tf:50-60` applies only `talos-worker-01`; `docs/plans/talos-two-worker-operations.md:46-49` points to a private directory `three-node-20260919-worker02-final`. Status: MISSING. Failure scenario: a common patch change (`patches/common.yaml`) is applied by CI to cp/worker-01 only; worker-02 drifts silently (e.g. kubelet serving-cert bootstrap). Fix: add a second `talos_machine_configuration_apply` for 10.0.0.225 gated by a `secondary_enabled` variable. Confidence: High.

**F7 — Severity: Medium.** Claim: no CPU, NUMA, or I/O isolation for latency-sensitive work.
Evidence: no `cpuManagerPolicy`, `reservedSystemCPUs`, `systemReserved`, or `topologyManager` in `config/environments/proxmox/homelab/talos/patches/*.yaml`; `live/proxmox/homelab/main.tf:24-31` `sockets = 1, cores = 38` with no `numa` block; `main.tf:52-53` `discard = "ignore"`, `iothread = false` on the 1200 GiB data disk; `docs/plans/proxmox-kubernetes-worker.md:114-116` asks for NUMA review but nothing records it (host appears to be an x3550 M4 class dual-socket, `docs/research/imm2-official-interfaces.md:151`). `docs/plans/talos-two-worker-operations.md:14-18` secondary array is write-through with failed CacheVault. Status: MISSING. Failure scenario: ollama's 29.5 vCPU spans two sockets while dind runners thrash the same L3; inference latency varies 2x and kubelet has no reserved CPU under pressure. Fix: enable `numa = true` and `iothread = true` (VirtIO SCSI single), set `machine.kubelet.extraConfig` `cpuManagerPolicy: static`, `reservedSystemCPUs`, `topologyManagerPolicy: single-numa-node`; keep AI Guaranteed. Confidence: Medium.

**F8 — Severity: Medium.** Claim: three deployment mechanisms coexist and Argo CD runs idle, budgeted, on the sleepy worker.
Evidence: Tofu `helm_release` with a Python post-renderer (`live/kubernetes/homelab-management/main.tf:22,29`), Kustomize via receipt-gated `kubernetes/platform/main/install.py:1-30`, and live UID-guarded patches "saved outside Git" (`kubernetes/platform/main/README.md:14-16`); Argo CD has `sourceRepos: []`, "no repo Secret or Application" (`README.md:80-81`) yet requests ~650m CPU/~1 GiB on primary (`kubernetes/platform/main/argocd/kustomization.yaml:16-30`). Status: IMPLEMENTED-BUT-FLAWED. Failure scenario: a placement change made by `plan.py --apply` is later reverted by a Helm upgrade path that bypasses the renderer, or vice versa; nobody can answer "what is the source of truth for this Deployment". Fix: pick one: either onboard the Tofu-managed charts into Argo CD Applications (Tofu keeps Talos/Cilium/Kueue only) or remove Argo CD until it owns something. Confidence: High.

**F9 — Severity: Low.** Claim: network datapath is the slowest supported Cilium mode and is enforced.
Evidence: `config/environments/talos/homelab/cilium-values.yaml:4-6` VXLAN tunnel, `kubeProxyReplacement: false`, `bpf.masquerade: false`; `live/talos/homelab/cilium.tf:38-47` postcondition forbids changing it. Status: IMPLEMENTED-BUT-FLAWED. Failure scenario: latency-sensitive east-west traffic pays VXLAN encapsulation plus iptables service NAT on a flat /24 where native routing is trivial. Fix: `routingMode: native`, `autoDirectNodeRoutes: true`, KPR on, after an acceptance run; relax the postcondition. Confidence: Medium.

**Strengths**

- Fail-closed CEL admission (`charts/homelab-queue/templates/admission.yaml`) enforces queue labels, scheduling gates, explicit requests and pool bounds without a webhook.
- Kueue AdmissionCheck integration with the power coordinator (`kueue.py`, `coordinator.py:409-449`) is a genuinely thoughtful wake-on-demand design with CAS-guarded status patches.
- Every image is digest-pinned and the AI chart refuses non-digest images (`_pod.tpl:3-4`).
- Talos node patches are minimal, explicit, and validated (`scripts/homelab-config-validate.py`).
- Placement is idempotent and hashed into Helm release inputs, so upgrades cannot silently lose it.
