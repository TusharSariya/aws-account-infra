# Explicit live quota acceptance

After the packaging stage is deployed, AI is intentionally off and both capacity collectors are healthy, dispatch `homelab-quota-acceptance` on `main` with confirmation `verify-disposable-quotas-and-reboot`. The protected `prod` workflow serializes with infrastructure applies. It reboots the worker and temporarily interrupts Pi-hole. Routine deployment never invokes this maintenance workflow.

Helm publishes separate administrator and consumer Job templates. The administrator has access only to the existing worker storage mount; the consumer has no host mount, token, secret or quota capability and runs in a Pod user namespace. Two fixed disposable project directories, `ai-quota-proof-first` and `ai-quota-proof-neighbor`, use reserved IDs 31990 and 31991 and 2 MiB hard limits. Their retained PV/PVC metadata and empty directories remain available for later explicit tests. Application data is outside the fixture set.

The consumer verifies its actual UID mapping, rejects project-zero reassignment and removal of project inheritance by an application owner, attempts at most 10 MiB against the 2 MiB limit, and verifies a neighboring write succeeds. It repeats the checks after the worker reboot and verifies fixture data and quota persistence. Cleanup removes only known files matching the current run nonce. The workflow checks Pi-hole UDP and TCP DNS afterward.

The `homelab-platform/quota-live-acceptance` ConfigMap records the reviewed template revision, filesystem UUID, node UID, before/after boot IDs and completion time. Each Job is fenced to the current boot, and node identity, boot and readiness are checked again after each Job. A mid-phase reboot cannot produce successful evidence. The reset workflow requires completed proof no older than 24 hours for the same templates, filesystem and current Ready worker boot before creating its reset receipt or Job. Missing, partial or stale proof blocks reset. This evidence does not establish backup or restore success.

If the workflow stops after recording `prepared` and the worker has rebooted, use `resume_verify: true` to run the second phase. An existing Job is accepted only for the same revision and boot; failed Jobs are never automatically retried. A `preparing` record, failed Job or unexpected fixture files require explicit inspection and a separately reviewed recovery scoped to these exact fixtures. Do not remove evidence to bypass a failed test.

Retained terminal AI Pod records are acceptable only when every regular, init and ephemeral container has a recorded exit. Pending, running or unknown container state blocks maintenance and reset. Isolated disposable Linux tests exercise helper behavior but do not substitute for this live Kubernetes proof. No live acceptance is claimed until a successful workflow run is recorded.
